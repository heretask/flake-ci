Release workflows and state machine

Release state comes from repository history, tags, commit policy, and prepared files. Examples use the default VERSION and CHANGELOG.md paths. Both filenames are configurable.

The bump baseline is the newest stable tag reachable from HEAD. Preparation parses Cog output once for both the strongest commit impact and the changelog, then computes the target and expected files together.

release rc compares VERSION and CHANGELOG.md with the expected preparation bytes. This detects both target changes and stale changelog content. An existing RC at HEAD is reused; otherwise, the target must differ from the latest stable release.

Full release lifecycle across cycles, including target escalation and the guarded chore-only state.

stateDiagram-v2
    [*] --> Unprepared: commits land after stable
    Unprepared --> Prepared: prepare + commit (VERSION=target, CHANGELOG written)
    Prepared --> RC: rc → vT-rc.N
    RC --> RC: rc at same HEAD (idempotent)
    RC --> Unprepared: fix keeps target, feat changes target and resets RC numbering
    RC --> Stable: stable at rc commit → vT (trusts VERSION + rc)
    Prepared --> Stable: stable without RC, prepared bytes must match
    Stable --> Unprepared: next impactful commit (new baseline = vT)
    Unprepared --> Unprepared: chore/docs only, target stays at latest stable

Run Release with the rc or stable channel. If preparation changes files, it opens a PR and stops. Merge the PR, wait for Nix checks, then rerun Release with the desired channel. After pushing the tag and channel, the job publishes a GitHub Release with the changelog notes. RCs are prereleases. Their notes show changes since the highest earlier RC number for the same version whose commit is an ancestor of the checkout. Stable releases and RCs without an eligible predecessor use the full stable-version section. Channel pushes notify Ops independently.

The shared release-request concurrency group allows one release request to run at a time without canceling the running request. Each run rechecks main. PR merges and Nix completions never start a release. Preparation PRs have no separate drift check. A failed notification can be retried independently. Unchanged channels, branch deletions, and revisions without the notification workflow do not notify Ops.
